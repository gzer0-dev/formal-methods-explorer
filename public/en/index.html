Formal Methods, Step by Step

Find the bugs your tests miss. Animated, step-by-step lessons on model checking, CSP refinement and property-based testing, written for test automation engineers.

Open the interactive lessons Source on GitHub

The interactive lessons are in Japanese. This page is an English overview of what they cover.

Why you can trust the numbers

No number on the site is hand-written: state counts, counterexamples and refinement results are computed by small checkers that run in the page (an explicit-state model checker, a CSP engine with trace, failures and failures-divergences refinement, and a property-based tester).

The same models are written in TLA+, Alloy and CSPM, and CI checks on every deploy that TLC, the Alloy Analyzer and ProB agree with the site. If they disagree, the site is not published.

Model checking

  1. States and transitionsDescribe an order workflow as states and the actions that change them.
  2. Exploring every stateBreadth-first search counts each state once, however many paths lead to it.
  3. Reading a counterexampleWalk back from the violating state to recover the shortest failing trace.
  4. Writing invariants"Never ship before payment" — and the one-step trace that breaks it.
  5. Finding deadlocksTwo threads take two locks in opposite orders and wait for each other forever.
  6. Does it ever finish?Liveness, retries and fairness: a loop that never ends is the counterexample.
  7. Fighting state explosionHow states grow, and how symmetry and normalisation shrink them.
  8. Reading temporal logicAlways, eventually, infinitely often and leads-to, on an elevator door.

Writing processes (CSP)

  1. Processes and eventsPrefix, external choice, recursion, STOP and SKIP.
  2. Parallel compositionA shared variable written as a process, and a lock that fixes the lost update.
  3. Specifications are processes tooTrace refinement: does the implementation only do what the specification allows?
  4. Telling processes apart by refusalsSame traces, different behaviour: failures refinement catches a printer that refuses colour.
  5. Dining philosophersEveryone holds one fork and waits for the other.
  6. Hiding reveals divergenceNothing happens on the outside while the inside loops forever.
  7. Including divergenceFailures-divergences refinement rejects an implementation that passes traces and failures.
  8. Checking algebraic lawsVerify CSP laws (and non-laws) by checking refinement in both directions.
  9. Transition rules, one step at a timeWhich operational rule produced each step, including the hidden τ steps.
  10. Determinism and flaky testsA test whose result wobbles is often a nondeterministic system — find where it comes from.
  11. From model to code and testsProcesses become threads; the verified model becomes the test oracle.

Case study: from design to implementation

  1. Designing the concurrent versionA three-input sorting network built from comparator processes (checked with 0s and 1s).
